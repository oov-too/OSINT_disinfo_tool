# Blocked output: the bisection and human-summary rule (standing, codified 2026-10-02)

Occasionally a passage of source text, or a passage an agent is about to write, is blocked by an API content filter: the model's output is refused, or an extraction fails, on that text. The ledger has handled this since the first blocked intake of 2026-09-27, when every attempt to catalogue the caption paragraph at 0:23:51 to 0:24:33 of an interview transcript was blocked; the owner read the transcript and entered a paraphrase of the speaker's quotation of a named official as claims row 1184 and timeline row 242, the rest of the paragraph stayed by pointer, and open-questions row 1 (kind guidance, standing) records the block. That is the model. The rule below is the same procedure made standing for every intake, analysis and Investigation run, with a marker, a queue and a tool so no block is lost and no agent stalls on one.

## 1. The procedure (every agent)

1. **Detect.** An output refused or an extraction failing on a passage counts as a block after the second attempt on the same unit. Do not retry a third time with the same text; do not rephrase the source to slip past the filter (a paraphrase that evades the filter is not the source and must not be entered as if it were).
2. **Bisect.** Split the unit (a document, a page, a transcript chapter, a table) in half and attempt each half; keep the half that fails; repeat until the smallest unit that still fails is found (a paragraph, a caption block, a line). Record every attempt and its result in `wip/<task>/bisect-<unit>.md` as the bulk-archive document run of 2026-10-01 did (`attempt: lines 1-7 verbatim` / `ok` or `blocked`), so the orchestrator can see what was tried and what passed.
3. **Capture.** Write `wip/<task>/blocked/<n>.md` with: the source location (file, lines or h:mm:ss, page), the deliverable location where the content belongs (note file, section, row number or timeline position), what the passage is about in one neutral sentence (a description, not the text), the bisection file, and the attempts made. Do not paste the blocked text itself into the capture file if writing it is what fails; the source location is the capture, because the owner has the source.
4. **Placeholder.** At the exact place in the deliverable, enter a pointer, never a gap: a claims row whose Claim cell reads `[BLOCKED: see the transcript at h:mm:ss; wip/<task>/blocked/<n>.md; awaiting human summary]` with the speaker, time and topic filled, Source class as the surrounding rows, Move `n/a`, and `attribution: n/a (pointer); chain: 1: <speaker> (n/a)`, Source class `host`, the Note cell "An API output filter blocked every attempt to catalogue this passage on <date>; the owner has the source" (the exact form of the first blocked intake's claims row 180 and audit row 19); the same marker form in an audit row, a timeline row, a quote or a prose section. Rows that depend on the blocked content cite the pointer row. The marker string `[BLOCKED:` is what tools/blocked_passages.py and the orchestrator search for.
5. **Log and continue.** Add the block to `progress.md`, to the reply JSON under `blocked_passages` (`[{"id","source","deliverable_location","about","bisect_file","attempts"}]`), and finish everything else. A block never ends a task.
6. **Queue.** The orchestrator runs `python3 tools/blocked_passages.py register <report.json or wip folder>` which appends the block to research/corrections/blocked-passages.md (the human-review queue: id, task, source location, deliverable location, about, status) with a permanent id `BP-<n>`.
7. **Human review.** The owner reads the source at the location and writes a summary (the precedent of the first blocked intake: a paraphrase in the owner's words, entered under the owner's name, never presented as the speaker's words). The summary goes in `wip/<task>/blocked/<n>.summary.md` or is given in chat.
8. **Splice.** `python3 tools/blocked_passages.py apply BP-<n> --summary <file>` replaces the marker in the deliverable with the summary text prefixed `owner's summary, entered <date>:` (in a claims row the Claim cell takes the summary and the attribution gains `owner's paraphrase, entered <date>`; the Note cell keeps `blocked output <date>: the passage itself is not restated; the owner has the source`), marks the queue row done, and adds a guidance row to the note's `## Open questions` in the form of the first blocked intake (kind guidance, Asked by `own: the database owner, <date>`, status standing) if one is not already there.
9. **Resume.** Any analysis that depended on the passage (cross-checks, timeline agreement, a speaker ledger cell ({{pack.speaker_ledgers}}), an Investigation strand) is re-run from that point with the summary in place, by relaunching the agent with "RESUME: the block at BP-<n> is now filled; continue from wip/<task>/progress.md", not from scratch.

## 2. What the summary is, and is not

The summary is the owner's reading, attributed as such, with the same evidentiary weight as any `own:` entry: it can carry a claims row (Source class as the speaker's statement would have had; the Note says it is the owner's paraphrase), a timeline row and a People row, and it can be cross-checked, but a quotation is never reconstructed from it. Where a later run needs the words (an echo check, a quotation-accuracy verification), the check is done by the owner against the source and reported as `own: the database owner, read against the transcript, <date>`.

## 3. Orchestrator and workflow duties

- Before launching, every brief carries the paragraph in section 5 below; every reply JSON schema includes `blocked_passages`.
- After every agent returns: search every deliverable for the marker with the Grep tool (pattern `\[BLOCKED:`, line numbers on) and register every hit, whether or not the agent reported it.
- The workflow script collects `blocked_passages` from every reply and returns them with the run result; the orchestrator writes them to the queue and tells the owner, in the hand-back message, how many blocks await summaries and where.
- An Investigation page with an unfilled marker in a load-bearing place is `Status: open, blocked at BP-<n>` in its Metadata until the summary lands; the judge scores it as it stands and notes the block.
- Archive: the bisect and blocked files go with the task folder to research/corrections/intake-logs/<task>/; the queue page keeps the row with its status.

## 4. The tool

`tools/blocked_passages.py`:
- `register <report.json | wip-folder>`: reads `blocked_passages` from the report (or every `blocked/*.md` under the folder), assigns `BP-<n>`, appends rows to research/corrections/blocked-passages.md, and writes the id back into the capture file.
- `scan [paths...]`: lists every `[BLOCKED:` marker in videos/, books/, research/ (or the given paths) with the file and line, and whether it is registered.
- `apply BP-<n> --summary <file> [--note <note.md>]`: splices the summary at the marker, updates the attribution and Note cells, marks the queue row done, and appends the guidance row to the note's `## Open questions` when the note has none for that block.
- `list [--open]`: the queue.

## 5. The paragraph every brief carries

> **Blocked output (standing rule, tools/filter-blocks.md).** If an output is refused or an extraction fails on a passage twice, do not retry a third time and do not paraphrase around the filter. Bisect the unit until the smallest failing piece is found, recording each attempt in `wip/<task>/bisect-<unit>.md`; write `wip/<task>/blocked/<n>.md` with the source location (file, lines or h:mm:ss, page), where in the deliverable it belongs, and one neutral sentence on what it is about (not the text); enter a pointer row at that place in the deliverable with the marker `[BLOCKED: see <source location>; wip/<task>/blocked/<n>.md; awaiting human summary]` (speaker, time and topic filled; Move n/a; `attribution: n/a (pointer); chain: 1: <speaker> (n/a)`, Source class `host`, the Note cell "An API output filter blocked every attempt to catalogue this passage on <date>; the owner has the source" (the exact form of the first blocked intake's claims row 180 and audit row 19)); note it in progress.md; list it in the reply JSON under `blocked_passages`; and finish everything else. The owner will read the source, write a summary, and the orchestrator will splice it in under the owner's name; your work resumes from there. Prevention: never pass a fetched text through your own output (copy files with the copy operation of the portable operations table, plugin/templates/briefs/operations.md); before each large output copy the unit's source material to `wip/<task>/current-unit.md` by that copy operation and name it in progress.md; write note parts of about 1,500 words and run `python3 tools/verbatim_check.py <part>` before writing each; record findings per source as you read.

## 6. The orchestrator layer (added 2026-10-02 after the W29 death)

Sections 1 to 5 assume the agent survives the block. In a Workflow or Agent run it does not: the API refuses the output, the harness's own retry is refused again, the agent dies without seeing the error, the script receives `null`, and the only signal is an "Error" chip (precedent: W29 of a batch intake of web posts, 2026-10-02 17:55 UTC, 12 minutes and 33 tool calls lost beyond the checkpoint, the refused output never existing so its trigger is unknowable). The layer below catches that case.

1. **Catch in the script.** Every fan-out runs through `tools/workflows/guarded-intake.js` (run with `Workflow({scriptPath: "tools/workflows/guarded-intake.js", args})`; the named-workflow registry did not list project copies on 2026-10-02, so scriptPath is the reliable call; args `{tasks:[{key, prompt, wip, resumePrompt?}], model, effort, maxResumes}`): a `null` result is logged, and the task is relaunched as a resume agent from its `wip/<task>/` checkpoint, up to `maxResumes` (default 2). The resume prompt carries the standing RESUME paragraph (continue from progress.md and parts/, do not redo recorded work, copy the unit in hand to `current-unit.md` before each large output, parts of about 1,500 words, fetched text never through the model's output).
2. **Health check.** `python3 tools/workflow_health.py [run] [--runlog]` reads the run's journal and transcripts and lists every agent as done, running or DEAD with its last error, last tool calls and files in play. The orchestrator runs it on every hand-back and at intervals during a long run; a screenshot is never the signal. `--runlog` appends the dead agents to research/corrections/blocked-runs.md (the run log, section 8); `--classify "<label>" "<class>" "<resolution>"` fills the row once the resume reports.
3. **Classify before bisecting.** If the resume passes the step where the first agent died, the block was *transient* (the precedent of 2026-10-01, a bulk-archive document run: every verbatim probe passed; one stop was the permission system) and is only logged. If the resume dies at the same step, the block is *reproducible*, and only then does bisection start. A probe that returns a refusal text rather than dying is *model-declined*, a different state from the API filter.
4. **Probe bisection** (section 7) runs over the unit the dead agent was handling, by probes that are allowed to die, never by the main agent.
5. **Two homes.** Reproducible passages that need the owner's summary go to the queue (research/corrections/blocked-passages.md, sections 1 to 4). Transient and terminal blocks go to the run log (section 8).

## 7. Probe bisection: `bisect-block`

`tools/workflows/bisect-block.js` (run with scriptPath; guarded-intake calls it by path; args `{file, minLines?, startLine?, endLine?, retries?}`) finds the smallest span of a file that the filter refuses without risking an Opus agent: a Haiku probe counts the lines; each probe prints a line range with a one-line Python read, `python3 -c "import sys; L = open(sys.argv[1], encoding='utf-8').read().split('\n'); print('\n'.join(L[int(sys.argv[2]) - 1:int(sys.argv[3])]))" <file> <a> <b>` (interim form; `ledger file lines` to build; the probe prompts in bisect-block.js still send `wc -l` and `sed -n` until phase 2 swaps them), and returns it verbatim as structured output; a probe that dies marks its range `blocked`, one that answers with a refusal is `model-declined`; the failing range is halved until a span of `minLines` (default 2) is isolated. About a dozen probes for a 2,000-word unit. Outcomes: `culprits` (the spans, each with its state), `lengthTriggered` when the whole fails but both halves pass (the fix is chunking, not a human summary), or `wholeBlocked: false` when nothing reproduces (transient; log only). The guarded-intake script calls it on `wip/<task>/current-unit.md` after the last resume dies; the orchestrator can call it directly on any file. From its result the orchestrator writes `wip/<task>/bisect-<unit>.md` (the attempts) and `wip/<task>/blocked/<n>.md` (the capture of section 1 step 3, with the line range as the source location), registers the capture with `tools/blocked_passages.py register`, and relaunches the resume with the pointer row in place. Which material to probe: `current-unit.md` if the agent kept it; else the files in play from the health check's last tool calls.

## 8. The run log

research/corrections/blocked-runs.md: one row per dead agent (date, run, label, time of death, last tool call, files in play, error text, classification, resolution), written by `workflow_health.py --runlog` and filled by `--classify`. It is the record that makes a pattern across runs visible (which step, which material); the queue stays reserved for passages awaiting the owner's summary.

## 9. Prevention

- **Fetched text never passes through the model's output.** Pages, PDFs, transcripts and feed bodies are saved by the acquisition tools or Python (`ledger acquire ...`, the copy operation of the portable operations table, a Python extraction) with headers prepended by Python; an agent's Write/Edit never carries a copy of a fetched text. The intake agents of 2026-10-02 already worked this way (every one of 13 used shell copies); it is now a rule.
- **Verbatim check.** `python3 tools/verbatim_check.py <draft> [--min 40] [--sources books/sources transcripts]` flags spans of 40 or more consecutive words identical to a held source. Agents run it on each note part before writing; the orchestrator runs it at integration. It enforces the quotation limit (a sentence or two of a copyrighted page) and removes the likeliest trigger.
- **Small output units.** Notes are written in parts of about 1,500 words; findings are written per source as it is read (`parts/findings.md`, "read, then record"), so a death costs one unit, not the reading.
- **The unit in hand.** Before each large output the agent copies the unit's source material to `wip/<task>/current-unit.md` by the copy operation (`python3 -c "import shutil; shutil.copyfile('<source>', 'wip/<task>/current-unit.md')"`, or for a line range of a larger file `python3 -c "import sys; L = open(sys.argv[1], encoding='utf-8').read().split('\n'); open(sys.argv[2], 'w', encoding='utf-8', newline='\n').write('\n'.join(L[int(sys.argv[3]) - 1:int(sys.argv[4])]) + '\n')" <source> wip/<task>/current-unit.md <a> <b>` (interim form; `ledger file copy` and `ledger file lines --out` to build)) and names it in progress.md (tools/agent-wip.md item 7).

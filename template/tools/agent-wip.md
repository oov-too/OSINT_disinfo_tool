# Agent work-in-progress checkpoints (standing rule, 2026-09-27)

Why: on 2026-09-27 a session limit killed eight agents mid-task (a 3h39m intake note and seven timeline era pages). None had written its report; three era files were half-written and two did not exist. Hours of agent work were lost. This must not happen again.

## The rule
0. At launch, the **orchestrator** writes `wip/<task-label>/prompt.md`: the exact prompt given to the agent, the paths of every brief it names, the model and effort, and the launch time. A resumed agent gets the same file plus a resume line. Nothing about a task should live only in the orchestrator's context.
1. Every delegated agent writes into `wip/<task-label>/` at the project root from its first minute, and updates it at every milestone (at least every 10 to 15 minutes of work, and before any long read or query):
   - `progress.md`: what is done, what is next, the files touched so far, and anything the orchestrator would need to resume without the agent's context. Overwrite it each time; keep it short.
   - the deliverable as it stands, when the deliverable is a new file (a note, a research page): write the destination file itself section by section (a partial note in `videos/` is better than none; mark it `Status: in progress` in its Metadata table until done), and keep a copy of any intermediate lists (catalogues, extracted rows, cross-check results) in `wip/<task-label>/`.
   - `report.json`: the JSON reply, built up incrementally (start with the keys and fill them as sections finish), so a killed agent's findings still reach the orchestrator.
2. The task is finished when the deliverables are in place and the final JSON is saved to `wip/<task-label>/report.json`, the agent replies, and the **orchestrator** deletes the folder after applying the report. Agents never delete their own wip folder. The orchestrator's hand-back then runs `python3 tools/wip_archive.py wip/<task-label> --run <run> --trash`: the deliverables (reports, progress, findings, onboard and hand-back files; never derived database caches or files over 50 MB, which the manifest lists) are kept under research/tasks/tool-feedback/<run>/<task-label>/ and the folder is moved to the Trash. Completed work does not stay under wip/ (owner ruling, 2026-10-22: a wip folder is work in progress, and a `check.db` or a sandbox copy is a cache, never a deliverable). Verification sandboxes (before/after copies) are trashed once their hand-back is accepted; only the hand-back pages stay.
3. On any resume (session reset, agent stall, rate limit), the orchestrator reads `wip/*/progress.md` first and relaunches each unfinished task with "resume from wip/<task-label>/", never from scratch.
4. `wip/` is outside the indexed folders (build_db.py and build_index.py read only videos/, books/, research/, subjects/), so partial files there never enter notes.db or the README. A partial note under videos/ marked `Status: in progress` does enter the DB; the orchestrator removes or finishes it on resume.
5. Task labels: short kebab-case with the date, e.g. `wip/intake-harrowmere-day12-0927/`, `wip/timeline-era-2009-2016/`.
6. Blocked output is part of checkpointing (standing rule, 2026-10-02, tools/filter-blocks.md): an API filter refusing an output or an extraction twice on one passage is bisected to the smallest failing unit, captured as `wip/<task>/blocked/<n>.md` (source location, deliverable location, one neutral sentence), entered in the deliverable as a pointer row with the marker `[BLOCKED: ...; awaiting human summary]`, noted in progress.md and in the reply JSON under `blocked_passages`, and the task continues. The orchestrator registers it with `python3 tools/blocked_passages.py register`, the owner writes the summary, and `apply` splices it in under the owner's name; dependent analysis resumes from there.
7. The unit in hand (standing, 2026-10-02, tools/filter-blocks.md section 9): before every large output (a note part, a source write-up, a long table) copy the source material of that unit to `wip/<task>/current-unit.md` without passing it through your own output, by `python3 -c "import shutil; shutil.copyfile('<source>', 'wip/<task>/current-unit.md')"`, or for a line range of a larger file `python3 -c "import sys; L = open(sys.argv[1], encoding='utf-8').read().split('\n'); open(sys.argv[2], 'w', encoding='utf-8', newline='\n').write('\n'.join(L[int(sys.argv[3]) - 1:int(sys.argv[4])]) + '\n')" <source> wip/<task>/current-unit.md <a> <b>` (interim form; `ledger file copy` and `ledger file lines --out` to build), and add one line to progress.md naming the unit and where it goes. If the agent dies on that output, the orchestrator bisects `current-unit.md` with the `bisect-block` probes instead of relaunching blind.
8. Read, then record: findings from each source are written to `wip/<task>/parts/findings.md` before the next source is read; note parts are about 1,500 words each and written as soon as they are drafted; fetched texts are copied by the copy operation of the portable operations table (plugin/templates/briefs/operations.md), never through the agent's own output (`python3 -c "import shutil; shutil.copyfile('<src>', '<dst>')"`; interim form; `ledger file copy` to build); `python3 tools/verbatim_check.py <part>` runs before a part is written.
9. Keep the computer awake (2026-10-25, after the forms measurement): before launching any workflow or agent that will outlast the orchestrator's turn, the **orchestrator** request keep-awake before launch and hold it until the run's last agent has replied: in the Claude desktop app its keep-awake tool (request_keep_awake, until the session is idle); elsewhere the system's own (macOS `caffeinate -i`, Linux `systemd-inhibit`, Windows the power plan or `powercfg /requestsoverride`). A sleeping computer kills the agent in flight (2026-10-24: a writer died mid-response and the guard's resume cost 4.8M records); a closed lid still sleeps.
